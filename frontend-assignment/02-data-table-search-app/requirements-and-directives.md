# Assignment 02 — Requirements & Directives

**v0.1 DRAFT — 2026-11-06**

## Part 1 — Requirements

### A. Functional requirements
- Table of synthetic records (suggested: id, name, category, status, owner, amount, updated_at).
- Text search (debounced), at least two filters (one multi-select), and sort on at least three columns.
- Pagination (server-driven) or virtualization. Justify the choice.
- Row detail view (drawer or page) reachable by link.
- All query state lives in the URL: search, filters, sort, page. Reload and back/forward restore the view.

### B. Mocked API (suggested, adjustable if documented)

| Method | Endpoint | Purpose |
|---|---|---|
| GET | /records | List with `q`, filters, `sort`, `page`, `pageSize`. Returns items and total |
| GET | /records/{id} | Record detail |
| GET | /facets | Filter options with counts (optional) |

- Mock must simulate latency, random 500 errors and an empty result.
- Handlers filter, sort and paginate on the "server" side, not in the client.

### C. UI states
- Loading (skeleton or spinner, no layout jump), empty (with a clear-filters action), error (with retry), partial refresh (keep old rows while fetching).
- Stale responses must never overwrite newer ones.

### D. Scenarios to address (answer in README)
- A user types fast in search. How do you avoid request floods and out-of-order responses?
- A shared URL is opened with an invalid sort or page. What happens?
- The result set drops while the user is on page 9. Where do they land?
- 50,000 rows instead of 5,000: what changes, and what do you measure?
- A screen reader user changes a filter. How do they learn the result count changed?
- Which data would you cache, for how long, and how is it invalidated?

### E. Performance reasoning
- State one budget (for example, interaction under 100 ms) and how you checked it.
- Avoid needless re-renders. Show one measured before / after or profiler finding.
- Keep the initial bundle small. Note anything you lazy-loaded.

### F. Live follow-up
The interviewer may ask you to add a **saved view** (named filter set), **column visibility toggle** or **CSV export of current view**, kept in the URL or local storage. Structure state so this is a small change.

## Part 2 — Directives

| ✅ Do | ❌ Don't |
|---|---|
| Treat the URL as the single source of truth for query state | Duplicate filter state in components and URL |
| Cancel or ignore stale requests | Let slow responses overwrite newer ones |
| Debounce search and keep input responsive | Fire a request per keystroke |
| Separate data fetching hooks from table presentation | Fetch inside presentational components |
| Use semantic table markup, labelled controls and live result counts | Build the table from unlabelled divs |
| Show loading, empty and error states with a recovery action | Show a blank screen on failure |
| Measure before optimizing and record the finding | Add memoization everywhere "just in case" |
| Mark AI-generated or reused code and verify it | Submit code you cannot explain |

- Mock API only (MSW, json-server or similar). Synthetic data only, generated by a seed script.
